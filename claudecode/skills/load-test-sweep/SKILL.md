# 負荷をかけて壊れるところを探す

★**芯はひとつ: 負荷を倍々に上げ、最初に「壊れた」段を見つけ、その手前との間を二分探索して限界を出す。**壊れたものを1つだけ、再現するテスト付きで直す。

bottleneck-sweep とは目的が違う。あちらは普段の待ち時間を縮める。こちらは限界と、限界の先で何が起きるかを見る。**正しいまま遅いだけ**のものはこちらでは直さず、報告に書いて bottleneck-sweep に回す。

仕事は3つ: **(A) 限界を測る、(B) 前回の限界と比べる、(C) 最初に壊れたものを1つ直す。**

## 0. 準備

- 既定ブランチの最新で作業する。`CLAUDE.md` と、そこから読まれる規則を読む
- ★**repo ごとの決まりは `CLAUDE.md` の `## Scouts` 節にある。**負荷試験の項に要るもの: 手元で起動するコマンド、負荷をかけるコマンド（シナリオ）、壊れていないことの確かめ方（不変条件）、上限（同時数・時間・データ量）、記録先。この skill より優先する。ただし下の「守ること」を緩めることはできない
- ⚠️ **Scouts 節に起動のコマンドと負荷のコマンドが無ければ、何も走らせない。**「Scouts 節に負荷試験の項が無い」と、足りないもの（どのサービスを・どう手元で起動し・依存を何で置き換えるか）を報告に書いて終わる
- repo の visibility を確かめる。公開 repo なら、PR・コミット・記録に数字以外（ホスト名・マシン・private repo）を書かない
- GitHub 操作は GitHub MCP か `gh api`（REST）。`search_*` は使わない

## 守ること（芯より先に効く）

- ⚠️ **負荷をかけてよいのは、この回に自分が起動し、loopback（`127.0.0.1`・`::1`・unix socket）だけで待ち受けるプロセスだけ。**負荷を送る前に、宛先のホストが loopback であることをコマンドの中で確かめ、違えば止める。本番・共有・staging・preview は、Scouts 節が許していても対象にしない。人が後から読む時には、もう負荷はかかった後だから
- ⚠️ **相手の依存も手元のものだけ。**DB・キャッシュ・外部 API・メール・決済は、メモリ上の DB やエミュレータ、スタブに置き換わっていること。外へ書きに行かないと示せないなら走らせない
- 上限: Scouts 節に無ければ、同時数 256・1段の窓 10 秒・合計 10 分・データ 100 万行まで。上限に達しても壊れなければ「上限まで壊れず」と書く。上限を上げて続けない
- 終わったら起動したプロセスを全部止め、ポートが空いたことを確かめる。残ったプロセスは次の測定を狂わせる
- 1段の窓は測定そのものなので、待ち時間として縮めない

## (A) 限界を測る（毎回）

1. **シナリオを並べる**。Scouts 節のシナリオを全部。軸は4つあり、Scouts 節が挙げたものだけ回す:
   - 同時数: 同時に飛んでいるリクエストの数
   - 頻度: 1秒あたりのリクエスト数（相手の応答を待たずに送る）
   - データ量: テーブルの行数やファイルの大きさを増やし、軽い負荷で応答を見る
   - 時間（soak）: 限界の 7 割の負荷を長くかけ、メモリ・fd・行数が増え続けないかを見る
2. **「壊れた」を決める**。どれか1つで壊れたとする:
   - エラー: 5xx・タイムアウト・接続拒否・プロセスの落下が 1% を超える
   - 結果の誤り: Scouts 節の不変条件が崩れる（件数の上限を超えて入った・同じ ID が2つ・合計が合わない）。★負荷試験で一番見つけたいのはこれ
   - 劣化: p95 が Scouts 節の予算（無ければ 1 秒）を超える
   - 漏れ: soak の間、メモリか fd が窓ごとに増え続ける
3. **倍々に上げる**。1, 2, 4, 8 … と1段ずつ上げ、各段で成功数・エラー数・p50・p95・不変条件を記録する。壊れた段で止める
4. **二分探索で詰める**。最後に壊れなかった段と最初に壊れた段の間を二分し、差が 1 割以下になったら止める。1点を3回測るのは、境目の判定が揺れたときだけ
5. **何で壊れたかを書く**。最初に壊れた理由（どのエラーか・どの不変条件か・どこの処理が詰まったか）と、壊れる直前の数字

## (B) 前回と比べる（Scouts 節に記録先があるとき）

- 各シナリオの限界を記録先にそのまま足す
- 直近4回の中央値より 2 割以上低く、測り直しても同じなら後退。前回の記録の commit から今の既定ブランチまでを二分探索して原因の commit を特定する。これがこの回の (C) の1本になる
- 全シナリオがそろって動いたなら入れ物（コンテナ・マシン）側の変化。報告に書くだけ
- ★毎回ちがう一行コマンドで測らない。足りないものがあれば Scouts 節が指す負荷のコマンドの方を直す（テスト付き。一度わざと壊して落ちるのを見る）

## (C) 最初に壊れたものを1つ直す

- 選ぶ順: 結果の誤り → エラー・落下 → 漏れ → 劣化。劣化だけで正しいなら直さず、報告に「bottleneck-sweep 向け」と書く
- ★**直す前に、壊れ方を再現するテストを書いて赤を見る。**負荷そのものを CI に持ち込まない。並行に2本投げる・行数を増やす、のように、壊れる条件だけを小さく取り出したテストにする
- 直した後、テストが green になり、(A) のそのシナリオで限界が上がったことを前後の数字で示す
- 挙動を変える直し（上限を足す・エラーを返す）は、壊れたときの今の挙動よりましだと PR に書く。仕様の判断が要るなら直さず、PR ではなく報告で人に聞く
- open な `routine:load-test-sweep` PR があれば新しく作らない。closed かつ未マージの PR で出した案と、Scouts 節の「やらないと決めたもの」は出さない

## PR の約束

- 新しいブランチ `fix/<short-desc>`。Conventional Commits、英語
- コミット identity と assignee は `## Scouts` 節に書かれたもの（無ければ git の設定のまま・assignee なし）
- push する前に Scouts 節の検査コマンドと、触った領域のテストを回す
- PR テンプレートがあれば埋める。本文に、どのシナリオで・どの段で・何が壊れたか、前後の限界、再現テストの赤と緑を書く。ラベル `routine` と `routine:load-test-sweep`（無ければ作る）。`subscribe_pr_activity` して CI を green にする
- **マージしない**

## 報告（1行目だけで分かる形）

```
🔨 load-test-sweep <repo>: 上限まで壊れず（シナリオ N 本）
🔨 load-test-sweep <repo>: <シナリオ> が <段> で <壊れ方> → PR <URL>（限界 <前>→<後>）
🔨 load-test-sweep <repo>: <シナリオ> の限界が後退 <前>→<今> → PR <URL>
⚠️ load-test-sweep <repo>: 測れなかった（理由）
```

2行目以降に、シナリオごとの限界（軸・壊れた段・壊れ方・その直前の p95）と、劣化だけで直さなかったもの、記録の URL。
