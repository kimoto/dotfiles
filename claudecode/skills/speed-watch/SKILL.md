# 人が待つものの速さを見張る

仕事は3つ: **(A) 人が待つものを全部測る、(B) 決まった項目の悪化を見る、(C) 人が週に失っている時間が一番大きいものを1つ速くする。**

★**手で呼んでも routine から呼んでも同じ手順。**(C) をいつやるか（間隔）は呼ぶ側が決める。手で呼ばれたら (C) もやる。

## 0. 準備

- 既定ブランチの最新で作業する。`CLAUDE.md` と `claudecode/rules/`（特に latency.md・hooks.md・ci-cost.md・experiments.md・tooling.md）を読む
- ★**repo ごとの決まりは `CLAUDE.md` の `## Scouts` 節にある。**速さの項（決まった項目を測るコマンドと記録先・走らせないスクリプト・測るときの注意・やらないと決めたもの）と検査コマンドはこの skill より優先する
- Scouts 節が無い repo でも (A) と (C) はできる。そのときは走らせないものを広めに取る（下の「走らせない」を全部）。(B) は記録先が無いので飛ばす
- 測る道具が入らないものは `n/a` のまま。速かったことにしない
- GitHub 操作は GitHub MCP か `gh api`（REST）。`search_*` は使わない

## (A) 人が待つものを全部測る（毎回）

1. **洗い出す**: 実行ビットか shebang のあるファイル、`package.json` の scripts、Makefile・justfile の target、hook の設定（lefthook・husky・`.claude/settings.json` の hooks・`.git/hooks`）と CI の workflow が呼ぶもの、シェルの起動で読まれるもの
2. **誰が待つかで分ける**。予算は Scouts 節に無ければ latency.md と hooks.md:
   - 人が打つ・キーやプロンプトから走る → 1 秒未満
   - pre-commit → 1 秒未満、pre-push → 10 秒未満、セッション開始の hook → 1 秒未満
   - CI だけ → 予算は ci-cost.md（分に切り上げて課金される。1分を越えるかが目安）
   - どこからも呼ばれないもの → 測らない（prune-sweep の仕事）
3. **測る**。一番安全な経路から:
   - テスト経由: テストランナーのテストごとの時間（bats `--timing`、pytest `--durations=0`、jest `--verbose` など）。テストが呼ぶスクリプトの遅さがこれで分かる
   - 直接: 読むだけ・検査だけのもの（lint・check 系、`--dry-run` があるもの）を、hook や CI と同じ引数で回す。3回の中央値
   - ⚠️ **走らせない**: install・setup・bootstrap・削除・push・ネットワークへ書くもの、人だけが走らせると決まっているもの、Scouts 節が挙げるもの。迷ったら走らせず、テスト経由の数字だけにする
4. **どれだけ使われるかを数える**。並べる順は「週あたりの回数 × 1回の待ち時間（予算を超えた分）」＝人が週に失っている時間。回数は本物の記録から取り、無ければ推定と書く:
   - CI: Actions の実行回数と時間（`gh api repos/OWNER/REPO/actions/runs`）
   - pre-commit・pre-push: 人がした commit と push の回数（`git log`。エージェントの commit は `Co-Authored-By: Claude` の行で見分けて除く。hook が入っているのは人の手元だけ）
   - キー・プロンプト・手で打つもの: 回数の記録は repo に無い。Scouts 節に使われ方の出どころ（履歴を集計するスクリプトなど）があればそれを使う。無ければ「起動のたび」「キーを押すたび」のように仕組みから推定し、推定と書く
   - ⚠️ 推定の回数だけで順位が決まるときは、その旨を報告に書く。本物の記録が取れる項目より上に置く根拠にしない
5. **サービス（API・Web ページ・バッチの応答）も対象にする。ただし Scouts 節に書いてあるときだけ**: 手元で起動する手順・測るコマンド（負荷のかけ方）・予算・回数の出どころ（アクセスログや APM の場所）。書いていなければサービスは測らず、報告に「Scouts 節に測り方が無い」と書く
   - ⚠️ **本番や共有の環境に負荷をかけない。**測るのは手元か、Scouts 節が測ってよいと書いた環境だけ。読むのはログと APM（読み取り）まで
   - 回数と時間は endpoint ごとに、ログや APM の本物の記録から取る（p50 と p95）。手元で測った数字は、直す前後の比較に使う
   - 予算は Scouts 節に無ければ、人が画面の前で待つ応答は 1 秒未満（latency.md）
6. 上の順で並べ、上位を報告に書く

## (B) 決まった項目の悪化を見る（Scouts 節に記録先があるとき）

- Scouts 節のコマンドで決まった項目を測り、出てきた結果を記録先にそのまま足す
- 記録の直近4回の中央値と比べ、1.25 倍を超え、測り直しても同じなら悪化
- 全項目がそろって動いたなら入れ物（コンテナ・マシン）側の変化。報告に書くだけで PR は出さない
- 1項目だけなら、前回の記録の commit から今の既定ブランチまでを二分探索して原因の commit を特定し、直す PR を出す（間隔に関係なくすぐ）
- ★毎回ちがう一行コマンドで測らない。決まった項目に足りないものがあれば、測るコマンドの方を直す（テスト付き。一度わざと壊して落ちるのを見る）
- ⚠️ 記録先が公開なら数字以外を書かない。ホスト名・CPU 名・private repo・どのマシンで使っているかは書かない

## (C) 速くする（呼ぶ側が決めた間隔で）

- (A) の並びで一番上（人が週に失っている時間が一番大きいもの）を1つ選び、速くする PR を1本。予算に収まっているものは選ばない
- ★挙動を変えない。キャッシュ・クエリ・並列化の変更は、テストで同じ結果になることを示せるものだけ。示せなければ報告に案として書くだけにする
- PR 本文に前後の数字（中央値・回数）を書く。1回で大差がつけば、追加の比較は要らない（experiments.md）
- 速くできない（待つこと自体が仕事: 測定の窓・転送・deploy）なら選ばず、次のものへ。latency.md の例外にあたるなら、遅い理由をその場所に書く PR でもよい
- open な `routine:speed-watch` PR があれば新しく作らない。closed かつ未マージの PR で出した案と、Scouts 節の「やらないと決めたもの」は出さない

## PR の約束

- 新しいブランチ `perf/<short-desc>`（スクリプトを足すなら `feat/`）。Conventional Commits、英語
- push する前に Scouts 節の検査コマンドと、触った領域のテストを回す
- PR テンプレートがあれば埋める。ラベル `routine` と `routine:speed-watch`（無ければ作る）、assignee kimoto。`subscribe_pr_activity` して CI を green にする
- **マージしない**

## 報告（1行目だけで分かる形）

「⏱ speed-watch: 予算超え N件、PR なし（悪化なし）」「⏱ speed-watch: <項目> が悪化 → PR <URL>」「⏱ speed-watch: 改善 PR <URL>（<対象> <前>→<後>ms）」「⚠️ speed-watch: 測れなかった（理由）」のどれか。2行目以降に、上位（対象・誰が待つか・1回の時間・週の回数と出どころ・週に失っている時間）と記録の URL。
