# 人が待つものの速さを見張る

仕事は3つ: **(A) 測って記録する、(B) 悪化していれば原因を直す、(C) 遅いものを1つ速くする。**

★**手で呼んでも routine から呼んでも同じ手順。**(C) をいつやるか（間隔）は呼ぶ側が決める。手で呼ばれたら (C) もやる。

## 0. 準備

- 既定ブランチの最新で作業する。`CLAUDE.md` と `claudecode/rules/`（特に latency.md・hooks.md・experiments.md・tooling.md）を読む
- ★**repo ごとの決まりは `CLAUDE.md` の `## Scouts` 節にある。**速さの項（測るコマンド・記録先・測るときの注意・やらないと決めたもの）と検査コマンドはこの skill より優先する
- ⚠️ Scouts 節に速さの項が無い repo では推測で進めない。何もせず「Scouts 節に速さの項が無い」と報告して終わる
- 測る道具が入らない項目は `n/a` のまま。速かったことにしない
- GitHub 操作は GitHub MCP か `gh api`（REST）。`search_*` は使わない

## (A) 測る（毎回）

- Scouts 節の測るコマンドを回す。出てきた結果を、Scouts 節の記録先にそのまま足す
- ★毎回ちがう一行コマンドで測らない。足りない項目があれば測るコマンドの方を直す（テスト付き。一度わざと壊して落ちるのを見る）
- ⚠️ 記録先が公開なら数字以外を書かない。ホスト名・CPU 名・private repo・どのマシンで使っているかは書かない

## (B) 悪化を見る（毎回）

- 記録の直近4回の中央値と比べ、1.25 倍を超え、測り直しても同じなら悪化
- 全項目がそろって動いたなら入れ物（コンテナ・マシン）側の変化。報告に書くだけで PR は出さない
- 1項目だけなら、前回の記録の commit から今の既定ブランチまでを二分探索して原因の commit を特定し、直す PR を出す（間隔に関係なくすぐ）

## (C) 速くする（呼ぶ側が決めた間隔で）

- 予算は Scouts 節に無ければ latency.md（人が待つものは 1 秒未満、pre-commit 1 秒未満、pre-push 10 秒未満）。予算から一番はみ出している項目を1つ選び、速くする PR を1本
- PR 本文に前後の数字（中央値・回数）を書く。1回で大差がつけば、追加の比較は要らない（experiments.md）
- open な `routine:speed-watch` PR があれば新しく作らない。closed かつ未マージの PR で出した案と、Scouts 節の「やらないと決めたもの」は出さない

## PR の約束

- 新しいブランチ `perf/<short-desc>`（スクリプトを足すなら `feat/`）。Conventional Commits、英語
- push する前に Scouts 節の検査コマンドと、触った領域のテストを回す
- PR テンプレートがあれば埋める。ラベル `routine` と `routine:speed-watch`（無ければ作る）、assignee kimoto。`subscribe_pr_activity` して CI を green にする
- **マージしない**

## 報告（1行目だけで分かる形）

「⏱ speed-watch: 記録のみ（悪化なし）」「⏱ speed-watch: <項目> が悪化 → PR <URL>」「⏱ speed-watch: 改善 PR <URL>（<項目> <前>→<後>ms）」「⚠️ speed-watch: 測れなかった（理由）」のどれか。2行目に記録の URL。
