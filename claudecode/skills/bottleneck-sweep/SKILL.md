# ボトルネックを見つけて直す

★**芯はひとつ: 待たされている時間 ＝ 週あたりの回数 × 1回の待ち（予算を超えた分）。**これが一番大きいところを、測ってから1つだけ直し、前後の数字で示す。どこを見るかの例は下にあるが、例に無いものでもこの物差しで測れるなら対象にする。

仕事は3つ: **(A) 待たされているところを測って並べる、(B) 決まった項目の悪化を見る、(C) 一番上を1つ速くする。**

★**手で呼んでも routine から呼んでも同じ手順。**(C) をいつやるか（間隔）は呼ぶ側が決める。手で呼ばれたら (C) もやる。

## 0. 準備

- 既定ブランチの最新で作業する。`CLAUDE.md` と、そこから読まれる規則を読む
- ★**repo ごとの決まりは `CLAUDE.md` の `## Scouts` 節にある。**速さの項（決まった項目を測るコマンドと記録先・走らせないもの・サービスの測り方・測るときの注意・やらないと決めたもの）と検査コマンドはこの skill より優先する
- Scouts 節が無い repo でも (A) と (C) はできる。そのときは下の「守ること」を一番きつく取る。(B) は記録先が無いので飛ばす
- 測る道具が入らないものは `n/a` のまま。速かったことにしない
- GitHub 操作は GitHub MCP か `gh api`（REST）。`search_*` は使わない

## 守ること（芯より先に効く）

- ⚠️ **本番や共有の環境に負荷をかけない。**測るのは手元か、Scouts 節が測ってよいと書いた環境だけ。本番はログと APM を読むまで
- ⚠️ **副作用のあるものは走らせない**: install・setup・bootstrap・削除・push・ネットワークへ書くもの、人だけが走らせると決まっているもの、Scouts 節が挙げるもの。迷ったら走らせず、テスト経由の数字だけにする
- ★**挙動を変えない。**キャッシュ・クエリ・並列化・処理の省略は、テストで同じ結果になることを示せるものだけ。示せなければ報告に案として書くだけ
- 待つこと自体が仕事のもの（測定の窓・転送・deploy）は速くする対象にしない

## (A) 待たされているところを測って並べる（毎回）

1. **洗い出す**。人か処理が待つものを全部。例えば:
   - スクリプト: 実行ビットか shebang のあるファイル、`package.json` の scripts、Makefile・justfile の target、シェルの起動で読まれるもの
   - hook: lefthook・husky・`.claude/settings.json` の hooks・`.git/hooks`
   - CI: workflow の job
   - サービス: API・Web ページ・バッチの応答。**Scouts 節に起動手順・測るコマンド・予算・ログの場所が書いてあるときだけ。**無ければ測らず「Scouts 節にサービスの測り方が無い」と報告に書く
   - どこからも呼ばれないものは測らない（prune-sweep の仕事）
   - 読んで探す: `review-performance` サブエージェントに repo のパスと「範囲 = repo 全体」を渡し、遅くなりそうな所を挙げてもらう。push 後の hook が差分に使うのと同じ見方。挙がったものは候補で、測って初めて順位に入れる
2. **予算を決める**。Scouts 節に無ければ: 人が打つ・キーやプロンプト・画面の前で待つ応答 → 1 秒未満、pre-commit → 1 秒未満、pre-push → 10 秒未満、セッション開始の hook → 1 秒未満、CI だけ → 分に切り上げて課金されるので、1分を越えるかが目安
3. **1回の待ちを測る**。安全な経路から:
   - テスト経由: テストごとの時間（bats `--timing`、pytest `--durations=0`、jest `--verbose` など）
   - 直接: 読むだけ・検査だけのものを、hook や CI と同じ引数で。3回の中央値
   - サービス: 本物の記録（ログ・APM の endpoint ごとの p50 と p95）。手元で測った数字は直す前後の比較に使う
4. **回数を数える**。本物の記録から取り、無ければ推定と書く:
   - CI: Actions の実行回数（`gh api repos/OWNER/REPO/actions/runs`）
   - pre-commit・pre-push: 人がした commit と push の回数（`git log`。エージェントの commit は `Co-Authored-By: Claude` の行で除く。hook が入っているのは人の手元だけ）
   - サービス: ログ・APM のリクエスト数
   - 手で打つもの・キー: 記録は repo に無い。Scouts 節に出どころがあれば使い、無ければ「起動のたび」のように仕組みから推定する
   - ⚠️ 推定の回数だけで順位が決まるときは、その旨を報告に書く。本物の記録がある項目より上に置く根拠にしない
5. **待たされている時間で並べ**、上位を報告に書く

## (B) 決まった項目の悪化を見る（Scouts 節に記録先があるとき）

- Scouts 節のコマンドで決まった項目を測り、結果を記録先にそのまま足す
- 記録の直近4回の中央値と比べ、1.25 倍を超え、測り直しても同じなら悪化
- 全項目がそろって動いたなら入れ物（コンテナ・マシン）側の変化。報告に書くだけで PR は出さない
- 1項目だけなら、前回の記録の commit から今の既定ブランチまでを二分探索して原因の commit を特定し、直す PR を出す。これがこの回の (C) の1本になり、open な `routine:bottleneck-sweep` PR があれば出さずに報告に書く
- ★毎回ちがう一行コマンドで測らない。足りないものがあれば測るコマンドの方を直す（テスト付き。一度わざと壊して落ちるのを見る）
- ⚠️ 記録先が公開なら数字以外を書かない。ホスト名・CPU 名・private repo・どのマシンで使っているかは書かない

## (C) 一番上を1つ速くする（呼ぶ側が決めた間隔で）

- (A) の並びで一番上を1つ選び、速くする PR を1本。予算に収まっているものは選ばない
- PR 本文に前後の数字（中央値・回数）と、週に何秒減るかを書く。1回で大差がつけば、追加の比較は要らない
- open な `routine:bottleneck-sweep` PR があれば新しく作らない。closed かつ未マージの PR で出した案と、Scouts 節の「やらないと決めたもの」は出さない

## PR の約束

- 新しいブランチ `perf/<short-desc>`（スクリプトを足すなら `feat/`）。Conventional Commits、英語
- push する前に Scouts 節の検査コマンドと、触った領域のテストを回す
- PR テンプレートがあれば埋める。ラベル `routine` と `routine:bottleneck-sweep`（付ける前に `"$(readlink -f ~/.claude/skills/bottleneck-sweep)/../../../bin/routine_labels.sh" routine:bottleneck-sweep` で色を揃えて無ければ作る。`gh` が無ければ飛ばす）、assignee は `## Scouts` 節に書かれた人（無ければ付けない）。`subscribe_pr_activity` して CI を green にする
- **マージしない**

## 報告（1行目だけで分かる形）

「⏱ bottleneck-sweep: 予算超え N件、PR なし（悪化なし）」「⏱ bottleneck-sweep: <項目> が悪化 → PR <URL>」「⏱ bottleneck-sweep: 改善 PR <URL>（<対象> <前>→<後>ms、週 <N> 秒減）」「⚠️ bottleneck-sweep: 測れなかった（理由）」のどれか。2行目以降に、上位（対象・誰が待つか・1回の時間・週の回数と出どころ・週に失っている時間）と記録の URL。
